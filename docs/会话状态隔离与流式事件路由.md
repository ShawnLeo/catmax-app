# 会话状态隔离与流式事件路由

> 适用范围：renderer 的 `messageStore` + main 的 `BackendManager` / `ClaudeAdapter`
> 解决问题：多 session 并发、切 session 时保留后台 turn 状态、流式 events 正确路由到 UI

## 1. 三种 id

一次 turn 涉及 3 个完全不同的 UUID，搞混任何一个都会导致 events 路由到错误的 session。

| id | 谁生成 | 用途 | 生命周期 |
|---|---|---|---|
| **catmax session.id** | main 创建 session 时 `randomUUID()` 写入 db 主键 | UI 选中会话 / `messageStore.sessionStates` 的 key / **envelope 路由** | 持久（db） |
| **backendThreadId** | backend 自己的内部线程 id（claude 首次是占位 UUID，后续会被真实 session_id 覆盖） | `claude --resume <id>` / `codex thread/send` | 持久（db `backend_thread_id` 字段） |
| **turnId** | `BackendManager.startTurn` 时 `randomUUID()` | envelope 的 `turnId` 字段 / `ClaudeAdapter.turnContexts` 的 key / `pendingApprovals` 的 requestId 前缀 | 单次 turn |

**最关键的不变量**：

```
envelope.sessionId === catmax session.id === messageStore.sessionStates 的 key
```

这条断了，UI 就看不到流式输出（用户切走再切回能恢复，是因为 loadHistory 从 db 读，跟流式链路无关）。

## 3. messageStore 内部结构

```
messageStore
│
├── currentSessionId: ref<string | null>        ← 当前选中的 catmax session
│   注意: 跟 sessionStore.currentSessionId 是两套独立 ref！（见 §5）
│
├── sessionStates: reactive(Map<sessionId, SessionState>)
│   │
│   │   ┌──────────────┬──────────────┬──────────────┬──────────────┐
│   │   │ "session-A"  │ "session-B"  │ "session-C"  │     ...      │
│   │   ├──────────────┼──────────────┼──────────────┼──────────────┤
│   │   │ messages[]   │ messages[]   │ messages[]   │              │
│   │   │ currentTurnId│ currentTurnId│ currentTurnId│              │
│   │   │ isRunning    │ isRunning    │ isRunning    │              │
│   │   │ pending...   │ pending...   │ pending...   │              │
│   │   │ lastError    │ lastError    │ lastError    │              │
│   │   └──────────────┴──────────────┴──────────────┴──────────────┘
│   │                                    ▲
│   └── cur() ─── sessionStates.get(currentSessionId) ───┘
│                  │
│                  ▼
│   对外暴露的 computed (messages / isRunning / pendingApproval / ...)
│   都走 cur() —— 即"当前 session 的状态"
│
└── 全局（不跟 session 绑定）
    ├── loading       ← loadHistory 时短闪
    └── globalError   ← currentSessionId 为 null 时的错误落点
```

**对外 API 用 computed + setter 模式**，让调用方代码不动：

```ts
// 调用方代码（不管切到哪个 session，都这么写）
messageStore.messages                  // 读：当前 session 的 messages
messageStore.pendingClaudePermission   // 读：当前 session 的 pending
messageStore.pendingClaudePermission = { ... }  // 写：自动落到当前 session
```

## 4. 切 session 时的多 turn 并发场景

这是整个改造的核心目的——切走 A 后 A 还在后台跑，状态不被清。

```
时间轴 ─────────────────────────────────────────────────────────────►

session-A:  [user 发消息] ──── claude 流式输出 ──── [权限请求] ──── ...
                                                          │
用户操作:                 ──[切到 B]──┐                  │
                                       │                  │
session-B:                  [B 自己跑] │                  │ A 还在后台跑
                                       │                  │ (main 进程不停)
                            ──[切回 A]─┘                  │
                                                          ▼
                                               切回 A 时 dialog 重新出现
                                               A 累积的 messages 都在
```

**为什么能保留**：

- **main 进程**：`ClaudeAdapter.turnContexts` 按 `turnId` 隔离，A 的 proc / bridge / mcp-config 都各自独立，互不影响
- **renderer**：`messageStore.sessionStates` 按 `catmax session.id` 隔离，A 的状态不被清
- **切 session 只动 `currentSessionId`**，不清 `sessionStates`
- **envelope 路由**：A 的 event 用 `clientSessionId=A` 路由 → 写到 `sessionStates.get('A')`，即使当前视图是 B，A 的 events 仍然累积；`pendingClaudePermission` 写在 A 的 state 里，切回 A 时自动显示

## 5. 两套 currentSessionId 的同步（最易踩坑）

`sessionStore.currentSessionId` 和 `messageStore.currentSessionId` 是两个独立的 ref，不会自动联动，必须在每个切换点同时调。

| 切换场景 | sessionStore | messageStore | 状态 |
|---|---|---|---|
| `SessionList.selectSession(id)` | `setCurrent(id)` | `setCurrentSession(id)` | ✅ 已同步 |
| `SessionList.newSession()` | `setCurrent('')` | `setCurrentSession(null)` | ✅ 已同步 |
| `SessionList.switchBackendTab()` | `setCurrent('')` | `resetAll()` (清空所有) | ✅ 已同步 |
| `SessionList.removeSession(id)` | `setCurrent(null)` (在 `remove` 内部) | `clearSession(id)` | ✅ 已同步 |
| ChatView 新建会话首条消息 | `setCurrent(id)` | `setCurrentSession(id)` | ✅ 已补 |

**曾经踩过的坑**：ChatView 新建会话时只调了 `sessionStore.setCurrent`，没调 `messageStore.setCurrentSession`，导致 `pushUserMessage` 里 `if (!currentSessionId.value) return` 直接 return，用户消息没进 store。

## 6. 主进程 per-turn 隔离（ClaudeAdapter）

claude 是 per-turn process 模型——每个 turn spawn 一个新 claude 子进程。多个 session 并发跑时，各自的子进程 / bridge / mcp-config 必须互不干扰。

```
ClaudeAdapter (单例)
│
├── turnContexts: Map<turnId, TurnContext>
│   │
│   │   ┌────────────────────┬────────────────────┐
│   │   │ turnId-A           │ turnId-B           │
│   │   ├────────────────────┼────────────────────┤
│   │   │ proc               │ proc               │  ← 各自的 claude 子进程
│   │   │ bridge             │ bridge             │  ← 各自的 Unix socket
│   │   │ mcpConfigPath      │ mcpConfigPath      │  ← 各自的 mcp-config.json
│   │   │ queue: TurnEvent[] │ queue: TurnEvent[] │
│   │   │ resolveWait        │ resolveWait        │
│   │   │ pendingApprovals   │ pendingApprovals   │  ← 各自的 Map
│   │   └────────────────────┴────────────────────┘
│   │
│   └── requestId 命名空间: `${turnId}:${bridgeRequestId}`
│       bridge 内部从 1 递增，两个 turn 都从 1 开始也不撞
│
├── interrupt(turnId)           ← 只清对应 context (kill 自己的 proc + stop bridge)
├── respondApproval(decision)   ← 拆 decision.requestId 最后一个 ':' 拿 turnId
└── dispose()                   ← 遍历所有 context 全清
```

**为什么不直接用 sessionId 做隔离**：同一个 session 理论上可以有多个并发 turn（虽然 Composer 的 `isRunning` 会禁用，但 main 进程不强制）。用 `turnId` 隔离粒度更细，且每个 turn 的资源（proc / socket 文件）天然唯一。

## 8. 常见 Bug 模式（排查 checklist）

**症状：发消息后看不到流式输出，切走再切回能从历史恢复**

→ envelope 路由 key 跟 store 索引 key 不一致。检查：

- [ ] `ChatView.startTurn` 是否传了 `clientSessionId`
- [ ] `manager.ts` 是否用 `args.clientSessionId ?? args.sessionId` 作为 envelope 的 sessionId
- [ ] 新建会话场景是否同步调了 `messageStore.setCurrentSession`
- [ ] `applyEvent` 收到的 sessionId 是否等于 `messageStore.currentSessionId`

**症状：切到 B 后 A 的 dialog 消失，切回 A 也没了**

→ 切 session 时清了 sessionStates。检查：

- [ ] `SessionList.selectSession` 是否误调了 `resetAll()` / `clearSession()`
- [ ] `messageStore.sessionStates` 里 A 的 state 是否还在（DevTools Vue inspector 看）

**症状：两个 session 同时跑，A 的 interrupt 误杀了 B**

→ per-turn 隔离失效。检查：

- [ ] `ClaudeAdapter` 是否还有遗留的 instance 字段（`currentProc` / `currentBridge` 等）
- [ ] `interrupt(turnId)` 是否精确按 turnId 找 context
- [ ] `respondApproval` 拆 requestId 时是否用 `lastIndexOf(':')`（bridgeRequestId 内部不含 `:`，但 turnId 是 UUID 也不含 `:`，所以 lastIndexOf 安全）

**症状：两个 turn 的 pendingApprovals 互相覆盖**

→ requestId 命名空间冲突。检查：

- [ ] requestId 是否是 `${turnId}:${bridgeRequestId}` 复合格式
- [ ] `respondApproval` 拆分时 turnId 部分是否正确还原
